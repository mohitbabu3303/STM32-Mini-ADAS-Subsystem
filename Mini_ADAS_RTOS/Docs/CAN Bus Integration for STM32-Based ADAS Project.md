# CAN Bus Integration for STM32-Based ADAS Project

This guide provides comprehensive suggestions for integrating CAN bus communication into your STM32-based Advanced Driver-Assistance Systems (ADAS) project, along with best practices for managing your GitHub repository.

## 1. CAN Hardware Integration

To enable CAN communication, your STM32 microcontroller needs an external CAN transceiver. The transceiver handles the physical layer of the CAN protocol, converting the digital signals from the STM32's CAN peripheral into differential signals suitable for the CAN bus.

### 1.1 Recommended Transceivers

Commonly used CAN transceivers include:

*   **MCP2551**: A robust and widely available high-speed CAN transceiver.
*   **TJA1050**: Another popular high-speed CAN transceiver with good performance.
*   **SN65HVD230**: A 3.3V CAN transceiver, suitable for direct interfacing with 3.3V STM32 microcontrollers without level shifting.

### 1.2 Wiring and Termination

CAN communication relies on a differential twisted pair cable (CAN_H and CAN_L) to minimize electromagnetic interference. Proper termination is crucial for signal integrity.

*   **CAN_H and CAN_L**: Connect these to the respective pins of your CAN transceiver.
*   **Termination Resistors**: A 120-ohm resistor should be placed at each end of the CAN bus. This prevents signal reflections and ensures reliable communication. For a simple two-node setup, you will need two 120-ohm resistors.
*   **MCU Pins**: On many STM32 microcontrollers, CAN1 typically uses PA11 (CAN_RX) and PA12 (CAN_TX). Refer to your specific STM32 microcontroller's datasheet and reference manual for exact pin assignments.

## 2. STM32CubeMX Configuration

STM32CubeMX simplifies the configuration of STM32 peripherals. Follow these steps to configure the CAN peripheral:

1.  **Enable CAN**: In STM32CubeMX, navigate to the `Connectivity` section and enable `CAN1` (or `CAN2`/`FDCAN` if available and needed).
2.  **Mode Selection**: 
    *   For initial testing and debugging, you can use **Loopback mode**. This allows the CAN peripheral to transmit and receive messages internally without needing a physical bus, which is useful for verifying your code logic.
    *   For actual communication on the bus, select **Normal mode**.
3.  **Baud Rate Configuration**: 
    *   ADAS applications typically use high baud rates, such as **500 kbps** or **1 Mbps**, for fast data exchange. 
    *   The baud rate is determined by the `Prescaler`, `Time Quanta (TQ)`, `Synchronization Segment (Sync_Seg)`, `Time Segment 1 (TS1)`, and `Time Segment 2 (TS2)` parameters. These values need to be carefully calculated based on your STM32's clock frequency to achieve the desired baud rate and sample point. STM32CubeMX often provides a tool to assist with this calculation.
4.  **Filter Configuration**: 
    *   CAN filters are essential in ADAS to process only relevant messages and reduce CPU overhead. Configure filter banks to accept specific CAN IDs. 
    *   You can set up filters to accept single IDs, ranges of IDs, or use mask-based filtering. For ADAS, you'll likely want to filter for messages from specific sensors (e.g., radar, camera) or control units.
5.  **Interrupts**: 
    *   Enable CAN RX interrupts (`CAN_IT_RX_FIFO0_MSG_PENDING` or `CAN_IT_RX_FIFO1_MSG_PENDING`) to handle incoming messages efficiently without polling. This is crucial for real-time ADAS applications.

## 3. HAL Code Implementation

After generating the code with STM32CubeMX, you'll implement the CAN communication logic using the STM32 HAL library.

### 3.1 Initialization

Ensure the CAN peripheral is initialized. The `MX_CAN1_Init()` function (generated by CubeMX) will handle the basic setup.

### 3.2 Transmitting CAN Messages

To send a CAN message, you'll need to populate a `CAN_TxHeaderTypeDef` structure and a data array.

```c
CAN_TxHeaderTypeDef TxHeader;
uint8_t TxData[8];
uint32_t TxMailbox;

// Configure TxHeader
TxHeader.StdId = 0x123; // Standard ID (11-bit)
TxHeader.ExtId = 0x0;   // Extended ID (29-bit) - not used for Standard ID
TxHeader.RTR = CAN_RTR_DATA; // Data frame
TxHeader.IDE = CAN_ID_STD;   // Standard ID
TxHeader.DLC = 8;            // Data Length Code (0 to 8 bytes)

// Populate TxData with your sensor or control data
TxData[0] = ...;
TxData[1] = ...;
// ...

// Add the message to the transmit mailbox
if (HAL_CAN_AddTxMessage(&hcan1, &TxHeader, TxData, &TxMailbox) != HAL_OK)
{
  // Error handling
  Error_Handler();
}
```

### 3.3 Receiving CAN Messages (using Interrupts)

Implement the `HAL_CAN_RxFifo0MsgPendingCallback()` (or `HAL_CAN_RxFifo1MsgPendingCallback()`) function to process incoming messages. This callback is triggered when a message is received in the FIFO.

```c
CAN_RxHeaderTypeDef RxHeader;
uint8_t RxData[8];

void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcan)
{
  if (hcan->Instance == CAN1)
  {
    if (HAL_CAN_GetRxMessage(hcan, CAN_RX_FIFO0, &RxHeader, RxData) == HAL_OK)
    {
      // Process received message
      // RxHeader.StdId contains the received ID
      // RxData contains the received data
      // Example: print received data
      printf("CAN Rx: ID=0x%X, Data=[%d %d %d %d %d %d %d %d]\n",
             RxHeader.StdId, RxData[0], RxData[1], RxData[2], RxData[3],
             RxData[4], RxData[5], RxData[6], RxData[7]);
    }
  }
}
```

Remember to enable CAN RX interrupts in your main code after initialization:

```c
if (HAL_CAN_ActivateNotification(&hcan1, CAN_IT_RX_FIFO0_MSG_PENDING) != HAL_OK)
{
  Error_Handler();
}
```

## 4. ADAS Specifics and DBC Files

For ADAS applications, CAN messages carry critical information from various sensors and control units. Standardizing these messages is vital.

### 4.1 ADAS Message Types

Consider the types of data your ADAS subsystem will send and receive:

*   **Sensor Data**: Radar object lists, LiDAR point clouds (or processed data), camera-based lane detection, traffic sign recognition, etc.
*   **Control Commands**: Steering angle commands, braking requests, acceleration/deceleration commands for adaptive cruise control, etc.
*   **Vehicle Status**: Vehicle speed, yaw rate, wheel speeds, gear position, turn signal status, etc.

### 4.2 DBC Files

A **DBC (Database CAN) file** is a crucial component in automotive CAN development. It defines the structure of CAN messages, including:

*   **Message IDs**: Unique identifiers for each message.
*   **Signals**: The individual data fields within a message.
*   **Scaling and Offset**: How raw CAN data bytes are converted into meaningful physical values (e.g., raw sensor value to meters/second).
*   **Units**: The units of the physical values.

Using DBC files allows different ECUs to interpret CAN messages consistently. Tools like `commaai/opendbc` [3] provide open-source DBC files for various vehicles, which can serve as a reference or starting point.

### 4.3 CAN FD for High Bandwidth ADAS

If your STM32 supports FDCAN (Flexible Data-rate CAN) and your ADAS application requires higher bandwidth (e.g., for raw sensor data or more complex object lists), consider using CAN FD. It allows for faster data rates and larger data payloads (up to 64 bytes per frame) compared to classic CAN's 8 bytes.

## 5. Integration with Your Existing Project (`Mini_ADAS_RTOS`)

Your current project uses FreeRTOS and UART for communication. Integrating CAN will involve adding the CAN peripheral and potentially modifying your FreeRTOS tasks.

### 5.1 Project Structure

Your `Mini_ADAS_RTOS` project has a standard STM32CubeIDE structure:

*   `Core/`: Contains `main.c`, FreeRTOS configuration, and interrupt handlers.
*   `Drivers/`: HAL drivers and CMSIS.
*   `Middlewares/`: FreeRTOS source files.

### 5.2 Integration Steps

1.  **STM32CubeMX**: Re-open your `.ioc` file in STM32CubeMX. Enable and configure the CAN peripheral as described in Section 2. Generate new code.
2.  **CAN Task**: Create a new FreeRTOS task (e.g., `CAN_Task`) responsible for handling CAN communication. This task could:
    *   Initialize the CAN peripheral.
    *   Manage CAN message transmission (e.g., sending vehicle status or control commands).
    *   Process received CAN messages (e.g., sensor data from other ECUs).
3.  **Data Exchange**: 
    *   Currently, your `autofilled` task generates `SensorData_t` and puts it into `sensorQueue`. The `DecisionTask` consumes this. 
    *   You can modify `autofilled` to send this data over CAN, or have `CAN_Task` receive actual sensor data via CAN and then put it into `sensorQueue`.
    *   Similarly, `AlertData_t` could be transmitted over CAN to an external display or control unit.
4.  **Error Handling**: Implement robust error handling for CAN communication, including bus-off states, error frames, and message retransmission strategies.

## 6. GitHub Push Guidelines

Maintaining a clean and organized GitHub repository is crucial for collaboration and project longevity. Here's what to push and what to avoid:

### 6.1 What to Push

*   **Source Code**: All your `.c`, `.h`, and `.s` files in `Core/`, `Drivers/`, and any new CAN-related files.
*   **STM32CubeIDE Project Files**: 
    *   `.ioc` file: This is essential as it contains your STM32CubeMX configuration, allowing others to regenerate the project.
    *   `.project`, `.cproject`: These are IDE-specific project files. While often large, they are necessary for importing the project directly into STM32CubeIDE.
*   **Linker Scripts**: `.ld` files (e.g., `STM32F103C8TX_FLASH.ld`).
*   **Documentation**: `README.md` (which you already have), any design documents, wiring diagrams, or explanations of your CAN message structure (even if not a formal DBC).
*   **DBC Files**: If you create or use specific DBC files for your ADAS messages, include them in a `Docs/` or `DBC/` folder.

### 6.2 What to Avoid Pushing (Use `.gitignore`)

*   **Build Artifacts**: 
    *   `.bin`, `.elf`, `.hex` files: These are generated during the build process and can be very large. They should not be committed to version control.
    *   `.map` files, `.o` files: Intermediate object files and memory maps.
*   **IDE-Specific User Files**: Files generated by the IDE for user preferences or temporary build data. For STM32CubeIDE, this often includes folders like `Debug/` or `Release/`.
*   **Sensitive Information**: API keys, private certificates, or other confidential data.
*   **Large Binary Assets**: Unless absolutely necessary and small in size, avoid large images, videos, or other binary files that are not directly part of the source code. Your `MINI ADAS BLOCK DIAGRAM.png` is acceptable as it's a small, relevant diagram.
